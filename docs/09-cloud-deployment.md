# 19. Cloud deployment

## Local development vs cloud deployment

| | Local development | Cloud deployment |
|---|---|---|
| Frontend | Vite dev server `localhost:5173` | Static build on a CDN (Vercel/Netlify/CloudFront), HTTPS |
| Backend | `uvicorn --reload` on your PC | Managed container/runtime (Render/App Runner/Lambda) with autoscaling and health checks |
| Database | SQLite file | Managed PostgreSQL with backups (Supabase/Neon/RDS) |
| Files | `storage_data/` folder | Private S3-compatible bucket |
| Secrets | `.env` file (git-ignored) | Platform env vars / Secrets Manager |
| URL | `localhost` (only you) | Public HTTPS URL (anyone, anywhere) |
| Logs | Terminal | Platform log stream / CloudWatch |
| Code changes needed | — | **None**, only environment variables |

## Approach A: free tier, student-friendly (recommended)

```
Vercel (React)  ──►  Render (FastAPI)  ──►  Supabase PostgreSQL
                                     └──►  Supabase Storage (S3 API)   [or Cloudflare R2]
```

Free-tier limits change over time. Check each provider's pricing page before a demo.

### Step 1: Push the repository to GitHub
See [13-github-and-proof-strategy.md](13-github-and-proof-strategy.md).

### Step 2: Database (Supabase PostgreSQL)
1. Create a free project at supabase.com (choose the region nearest to you, e.g. Mumbai `ap-south-1`).
2. **Project Settings → Database → Connection string → URI**. Use the **Session pooler** string, because Render reaches it over IPv4:
   `postgresql://postgres.<ref>:<password>@aws-0-ap-south-1.pooler.supabase.com:5432/postgres`
3. Keep it for `DATABASE_URL`. Tables are created automatically on first start.

*Alternative:* Neon.tech → create project → copy the connection string (add `?sslmode=require` if not present).

### Step 3: Object storage (Supabase Storage via S3 API)
1. **Storage → New bucket** → name `assignment-submissions` → **Public bucket OFF**.
2. **Project Settings → Storage → S3 Connection**: copy the *Endpoint* and *Region*, then **New access key** → copy the Access key ID and Secret.
3. Values:
   ```
   STORAGE_PROVIDER=s3
   S3_BUCKET=assignment-submissions
   S3_ENDPOINT_URL=https://<ref>.supabase.co/storage/v1/s3
   S3_REGION=ap-south-1
   S3_ACCESS_KEY_ID=…
   S3_SECRET_ACCESS_KEY=…
   ```
*Alternative:* Cloudflare R2 → create bucket → *Manage R2 API tokens* (Object Read & Write) → endpoint `https://<account-id>.r2.cloudflarestorage.com`, region `auto`.

### Step 4: Backend (Render)
1. render.com → **New → Blueprint** → select your repo. Render reads `render.yaml`.
2. Fill the `sync: false` values: `DATABASE_URL`, the `S3_*` values, `CORS_ORIGINS` (your Vercel URL, set after Step 5), `PUBLIC_API_URL` (`https://<service>.onrender.com`). `SECRET_KEY` is generated by Render.
3. Deploy. The logs should show `Database engine created (dialect=postgresql)` and `Using S3-compatible object storage`.
4. Visit `https://<service>.onrender.com/api/health` → `"status": "ok"`.
5. Seed demo data once: Render **Shell** tab → `SEED_DEMO_PASSWORD='YourDemoPass1' python -m backend.seed`.

*Without the blueprint:* New Web Service → Python → Build `pip install -r requirements.txt` → Start `uvicorn backend.app:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips="*"` → Health check path `/api/health` → add the env vars. Or choose **Docker** and Render uses the `Dockerfile`.

### Step 5: Frontend (Vercel)
1. vercel.com → **Add New Project** → import the repo → **Root Directory: `frontend`** → framework *Vite*.
2. Environment variable `VITE_API_URL=https://<service>.onrender.com`.
3. Deploy → `https://<project>.vercel.app`. `vercel.json` rewrites all routes to `index.html` so refreshing `/assignments/3` works.
4. Put this URL in Render's `CORS_ORIGINS` and redeploy the backend.

*Netlify:* base directory `frontend`, build `npm run build`, publish `dist` (`netlify.toml` included).

### Step 6: Authentication
Built into the backend (bcrypt + JWT). In the cloud, the only change is that `SECRET_KEY` lives in Render's encrypted env vars. HTTPS is automatic on Render and Vercel.

### Step 7: CI/CD
* GitHub Actions (`.github/workflows/ci.yml`) runs the tests, frontend build and Docker build on every push and PR.
* Render and Vercel **auto-deploy** when `main` changes. Together that is a complete CI/CD pipeline.

### Step 8: Monitoring
* Render → *Logs* (structured lines with `request_id=`) and *Metrics* (CPU/RAM/requests).
* Free uptime monitor (UptimeRobot / Better Stack) pinging `/api/health` every 5 min. It also keeps the free instance warm.
* Admin → **Users & audit** in the app for the security audit trail.

## Approach B: AWS / Azure / GCP architecture

### AWS mapping

| Component | AWS service | Notes |
|---|---|---|
| Frontend | **S3 (static website) + CloudFront** | `npm run build` → `aws s3 sync dist s3://handin-web` → CloudFront distribution with custom error 403/404 → `/index.html` |
| Backend | **Lambda** (`backend.lambda_handler.handler`) or **App Runner** / ECS Fargate (Dockerfile) or EC2 (IaaS) | Lambda = serverless; App Runner = simplest container PaaS |
| API | **API Gateway (HTTP API)** | Routes `ANY /{proxy+}` → Lambda; throttling (e.g. 50 rps burst per client), custom domain, TLS |
| Database | **RDS PostgreSQL** (Multi-AZ, automated backups) + RDS Proxy for Lambda | or DynamoDB with a key design like `PK=ASSIGNMENT#7, SK=STUDENT#12` |
| Files | **S3** private bucket | Block Public Access, SSE-KMS, versioning, lifecycle → Glacier after 1 year |
| Authentication | **Cognito** user pools (optional) | Replace `decode_access_token` with Cognito JWKS verification; groups `students` / `teachers` → roles |
| Secrets | **Secrets Manager / SSM Parameter Store** | `SECRET_KEY`, DB password |
| Logs & metrics | **CloudWatch** Logs, Metrics, Alarms; X-Ray | alarm on 5xx rate and `/api/health` failures |
| Security edge | **WAF** on CloudFront/API Gateway | rate-based rules, OWASP managed rules |
| Async work | **SQS + Lambda** / EventBridge | S3 `ObjectCreated` → virus scan, email notifications |
| IaC | CloudFormation / CDK / Terraform | reproducible environments |

Lambda quick start (container image):

```bash
# Lambda Python base image; handler = backend.lambda_handler.handler
aws ecr create-repository --repository-name handin-api
docker build -t handin-api -f Dockerfile .   # or a Lambda-specific Dockerfile FROM public.ecr.aws/lambda/python:3.12
# push to ECR, create the function from the image, attach an IAM role with the S3 policy
# from docs/05-cloud-storage-design.md, set env vars, and add an HTTP API trigger.
```

### Azure equivalents
Static Web Apps (+ Front Door CDN) · API Management · **Azure Functions** or **Container Apps** / App Service · **Azure Database for PostgreSQL – Flexible Server** · **Blob Storage** (private container, **SAS URLs** = signed URLs; the S3 code would need an Azure Blob provider class) · **Microsoft Entra ID** · **Key Vault** · **Azure Monitor / Application Insights**.

### GCP equivalents
Firebase Hosting or Cloud Storage + **Cloud CDN** · **API Gateway** · **Cloud Run** (runs the Dockerfile as-is) or Cloud Functions · **Cloud SQL for PostgreSQL** · **Cloud Storage** (V4 **signed URLs**; also S3-interoperable via HMAC keys, so `S3_ENDPOINT_URL=https://storage.googleapis.com` works) · **Identity Platform / Firebase Auth** · **Secret Manager** · **Cloud Logging & Monitoring**.

## Deployment checklist

- [ ] `ENVIRONMENT=production` and a strong `SECRET_KEY` (the app refuses to start without one)
- [ ] `DATABASE_URL` points to managed PostgreSQL (not SQLite, because container disks are ephemeral)
- [ ] `STORAGE_PROVIDER=s3`, bucket **private**
- [ ] `CORS_ORIGINS` = exact frontend URL(s), no wildcard
- [ ] `PUBLIC_API_URL` set
- [ ] Health check path `/api/health`
- [ ] Demo data seeded (fictional) with a non-default password
- [ ] Billing alerts on (AWS/Azure/GCP)
